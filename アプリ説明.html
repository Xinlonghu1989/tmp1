AI経営診断アプリ　説明資料

今回の主要変更点と開発者向けの全体説明／2026年8月16日時点の実装に準拠

今回の改修で、運用に直接効く変更は次の3点です。いずれも 「触る場所を1か所に決める」という同じ考え方に立っています。 アプリを長く使ううえで、迷ったときにどこを見ればよいかが決まっていることが、 機能の数より効きます。

変更点何が変わったか触る場所
1. APIキーの統一管理 鍵の置き場が複数に散っていたのを、アプリ直下の .env 1ファイルに集約。 参照できるキーの一覧（登録簿）をコード側に持たせ、未設定は起動ログで分かるようにした .env
2. データパイプライン 資料の取り込み口を pipeline.py 1本に統一。フォルダに入れて更新を実行すれば、 変わった分だけが検索用DBに反映される。分類フォルダは自由に増やせる data_internal/
3. LLMの切り替え プロンプトの文面を ai_prompts.py 1ファイルへ集約。使うモデルは .env の1行で切り替わる。モデルごとの作法の差はアプリが自動で吸収する .env

1APIキー類の統一管理

LLMのキーも、外部データ提供元（e-Stat・EDINET・J-Quants など）のキーも、 画面ログインのパスワードも、置き場は .env ただ1つです。

改修前 アプリ直下の .env、親フォルダの設定ファイル、単独の鍵ファイル、 ソース内の既定値と、鍵が複数箇所に分散していました。 どれが使われているのかを追えず、差し替え漏れを招く構成です。
改修後 .env 1ファイルのみ。コードからは settings.credential() を 通してしか読めない。登録簿に無い名前を読もうとすると、その場で誤りとして落ちる。

1.1 設定できるキーの一覧

アプリが参照するキーは次の8件で、すべて settings.CREDENTIALS に登録済みです。 ここに無い名前は読み込めません（読もうとした時点でエラーになるため、 タイプミスが静かに「未設定」として通ることがありません）。

キー名用途未設定だとどうなるか
ANTHROPIC_API_KEY AI機能すべて（経営AI相談・計画診断・総会QAアプリ） AI機能が「AI未接続」表示になる
ANTHROPIC_BASE_URL LLMの接続先（Amazon Bedrock） 既定値を使う
ANTHROPIC_MODEL 使うモデル（→ 変更点3） 既定モデルを使う
APP_CREDENTIALS 画面を開くときのログイン 起動できない
FRED_API_KEY為替（ドル円） その指標が「未連携」表示になる
ESTAT_APP_ID人口・賃金・短期滞在入国者数・建設資材 同上
EDINET_API_KEY有価証券報告書の取得 同上
JQUANTS_API_KEY株価・財務データ 同上
MLIT_IN_API_KEY不動産価格指数・地価 同上
「未連携」表示はエラーになりません 外部データのキーが未設定でも、アプリはエラーを出さず「未連携」と表示して動作を続けます。 数値が空欄である理由が仕様なのか設定漏れなのかを判別できるよう、 未設定のキーは起動ログに一覧で表示されます。起動時にご確認ください。

1.2 操作方法

初めて設定するとき

  1. ひな形をコピーして .env を作る 
    cp .env.example .env
  2. テキストエディタで .env を開き、= の右側に値を書く。 使わない提供元は空のままで構いません 
    # 例
ANTHROPIC_API_KEY=sk-（実際のキー）
ESTAT_APP_ID=（実際のID）
FRED_API_KEY=
  3. アプリを起動し、ログで設定状況を確認する 
    python3 app.py
    [OK] LLM: 接続設定あり（model=anthropic.claude-opus-4-8｜Claude Opus 4.8／接続先=bedrock-mantle.ap-northeast-1.api.aws）
[情報] 未設定のキー（.env）:
       - FRED_API_KEY｜為替（ドル円）

キーを差し替えるとき

.env の該当行を書き換えて、アプリを再起動するだけです。 コードの変更は要りません。データ取得のキーだけを替えた場合は、次の更新実行から新しいキーが使われます。

設定状況だけを確認したいとき

python3 pipeline.py status

末尾に未設定のキーが並びます。アプリを起動せずに確認できます。

キーと接続先は必ず同じ出所から読みます 実行環境に ANTHROPIC_BASE_URL などが設定されていると、 .env の値と混在してキーと接続先が食い違うおそれがあります。 これを避けるため、キーが .env 由来であれば接続先も .env の値を使う という規則を設けています。起動ログには実際に使う接続先ホストを表示するため、 意図した接続先で動いているかはログで確認できます。
納品前に必ず実施してください 現在 .env に入っているAPIキーと APP_CREDENTIALS のパスワードは、 開発中に配布したファイルにも含まれています。 すべて発行し直して（ローテーションして）ください。 改修で削除した未参照の鍵ファイルの分も含め、発行元で古い鍵を失効させてください。

2データパイプライン

資料の取り込み口は pipeline.py というコマンド1本だけです。 「どこに置いて、何を実行すれば、いつ検索に出るのか」が一意に決まります。

2.1 データの置き場は3つだけ

フォルダ中身誰が入れるか
data_external/ HHHD公表IR資料、有価証券報告書、監視指標の原票CSV パイプラインが自動取得
data_internal/ 経営会議議事録、株主総会議事録、中期経営計画、IR公表資料、社内資料 人がフォルダへ置く
runtime_data/ 検索用DB、生成したレポート、ログ、AIとのやり取りの履歴 アプリが書き出す

2.2 操作方法

資料を追加する（いちばんよく使う操作）

  1. 分類のフォルダに資料をドラッグ&ドロップで入れる 
    data_internal/経営会議議事録/2026年8月_経営会議.docx
  2. 反映コマンドを実行する 
    python3 pipeline.py update --internal
  3. 反映されたか確認する 
    python3 pipeline.py status
差分だけを読み直します 前回から変わっていないファイルは読み直さず、計算済みの検索用データを再利用します。 数百件が収録されていても、追加が1件であれば数秒で完了します。 全件を作り直す場合は数分を要するため、日々の運用ではこの差が大きく効きます。

分類（フォルダ）を増やす

フォルダを作るだけです。コードの変更は要りません。

mkdir data_internal/取締役会資料      # 名前は自由。日本語で構わない
# 資料をこのフォルダへ入れる
python3 pipeline.py update --internal

次回以降、pipeline.py status にも、画面のアップロード先の選択肢にも、 この分類が自動で並びます。フォルダを消せば分類も消えます （検索用DBからも次の更新時に外れます）。

画面の選択肢へ反映するにはアプリの再起動が必要です アップロード先の選択肢は、画面を組み立てる際に1回だけ読み込むためです。 検索への反映（update）は再起動なしで有効になります。

すべてのコマンド

コマンド用途
pipeline.py update外部取得 → 内部取込 → 検索用DBへ差分反映（通常はこれ）
pipeline.py update --internal手で置いた資料だけ反映する（速い）
pipeline.py update --external外部データだけ取得する
pipeline.py update --force期限前でも外部を全件取り直す
pipeline.py statusフォルダ別の件数と検索用DBの状態を見る
pipeline.py rebuild検索用DBを作り直す（通常は不要。数分かかる）

3LLMの切り替え

AIへの指示文（プロンプト）は ai_prompts.py 1ファイルに集約してあります。 使うモデルは .env の1行で切り替わり、 プロンプトも呼び出し方も変更は要りません。

3.1 プロンプトの保守は1ファイルに集約済み

AIへ送る指示文は、すべて ai_prompts.py の中にあります。 各画面のコード（app.py・agm/service.py・knowledge_rag.py）は 「どの指示文を使うか」を選ぶだけで、文面そのものは持っていません。 

# 呼び出し側は常にこの形。文面はここには書かない
messages = ai_prompts.agm_answer_messages(question, category, evidence, ...)
result   = ai_client.call_chat_json(messages, feature="agm.answer")

機能別の指示文は ai_prompts.py に集約しています。

画面・機能指示文
経営AI相談 interpret_messages（質問の解釈）、assistant_messages （自由質問・原稿支援・計画示唆・シナリオ・診断深掘りの5種）
経営ダッシュボードdashboard_messages
計画診断diagnosis_messages
資料検索knowledge_messages
総会QAアプリ agm_question_messages（想定質問の予測）、agm_answer_messages（回答案）、 agm_review_messages、agm_question_set_review_messages、 agm_table_summary_messages、agm_import_enrichment_messages、 agm_consolidation_messages（BU・HHHD統合）、 agm_executive_summary_messages、agm_rehearsal_messages
この集約はテストで担保しています tests/test_llm_switching.py が、ai_prompts.py 以外のファイルで AIへのメッセージを組み立てていないことを検査します。 画面側に文面を書くとテストが落ちるため、同じ文面が複数箇所に分散することを防げます。

3.2 モデルの切り替え方

.env のこの1行を書き換えて、アプリを再起動するだけです。

ANTHROPIC_MODEL=anthropic.claude-opus-4-8

候補の一覧を見る

python3 ai_client.py
■ 使用中のモデル: anthropic.claude-opus-4-8
  設定箇所: .env の ANTHROPIC_MODEL
  接続先  : https://bedrock-mantle.ap-northeast-1.api.aws/anthropic

■ 切り替え候補（.env に書く値）
  ★使用中 anthropic.claude-opus-4-8     上位
     anthropic.claude-opus-4-7     上位
     anthropic.claude-haiku-4-5    軽量

本当に使えるかを実測する

python3 ai_client.py --probe

各候補へ実際にごく短い質問を送り、応答が返るかを確かめます。 利用できるモデルは契約内容で変わるため、 候補一覧と実態がずれていないかはこのコマンドで確認できます。

接続先（Amazon Bedrock）が実際に提供しているモデルを、2026年8月16日に実測した結果です。

モデル特徴 応答速度

「未提供」は現在の契約で使えないという意味です モデルIDとしては正しく、アプリ側の作法（後述）も登録済みですが、 現在の接続先へ送ると 404 does not exist が返ります。 契約で使えるようになったら、ai_client.MODELS の該当行の available を True にするだけで候補に並びます。 プロンプトも呼び出し側も変更は要りません。

3.4 モデルごとの作法の違いはアプリが吸収する

モデルを替えると、実は送信の作法が変わります。ここを手作業で合わせる設計だと、 切り替えた瞬間に全AI機能が止まります。そこで違いを ai_client.MODELS という表に持たせ、送信時にアプリが自動で合わせています。

違い放置するとどうなるかアプリの対応
温度指定
（temperature）		 新しい世代（Opus 4.7以降）はこの指定を廃止しており、送ると400エラーとなり AI機能が停止する。一方 Haiku 4.5 では使える モデルごとに送るか送らないかを表から判断する
思考トークン 思考が既定でONのモデル（Opus 5 / Sonnet 5）では、 思考の分も出力の上限に数えられる。従来と同じ上限のままだと回答が途中で切れる 該当モデルのときだけ出力枠を自動で広げる
出力の上限 モデルごとに上限が違う（Haiku は他より小さい）。超えると400エラー モデルの上限で頭打ちにする
安全性による拒否 新しい世代は安全性の判断で回答を控えることがある。 このとき通信は成功扱い（HTTP 200）で本文が空になるため、 回答が得られていないことを画面が判別できない 明示的に失敗として扱い、画面に「AI未接続」相当の但し書きを出す
3モデルでの動作を確認しています 経営AI相談の質問解釈プロンプト（716文字）を、opus-4-8 / opus-4-7 / haiku-4-5 の3モデルへそのまま送り、 いずれも同じ構造（intent / search_query / series / next_step）のJSONを返すことを確認しています。 温度指定は haiku-4-5 にのみ送られ、他の2つには送られません。 この差はアプリが自動で吸収します。

3.5 どのモデルを選ぶべきか

状況推奨
通常運用 anthropic.claude-opus-4-8（既定のまま）。 診断文・回答案の品質がこのアプリの価値の中心であり、 応答速度の差（1〜3秒）はそれに見合いません
上位モデルが不調・停止のとき anthropic.claude-opus-4-7 へ退避。品質はほぼ同等です
大量の資料を一括で分類・要約したいとき anthropic.claude-haiku-4-5。ただし 診断文・回答案の生成には使わないでください（内容が浅くなります）

2全体像

2.1 設計の中心にある3つの約束

約束意味守っているもの
取り込み口は1つ 資料が検索に入る経路は pipeline.py と画面アップロードのみ。 両者とも knowledge_rag の同じ関数を通る pipeline.py
鍵の置き場は1つ APIキーは .env のみ。読み出しは settings.credential() 経由 settings.py
指示文の置き場は1つ AIへの指示文は ai_prompts.py のみ。画面側は選ぶだけ ai_prompts.py

2.2 ダミーデータを置かない方針

画面に出る数値・文章は、必ずどこかの実データかLLMの生成物です。 コード内にそれらしい既定値を書いてはいけません。データが無い場合は 「未連携」／「取得待ち」と表示し、 「無い」ことが分かる形にします（data.py の _ext() / _internal()）。 もっともらしい数値が出ると、それが実測なのか仮なのかを画面から判別できなくなるためです。

4データの流れ

4.1 差分更新の仕組み

更新のたびに全件を読み直すと数分かかるため、変わったファイルだけを処理します。 判定にはファイルの内容から作る指紋を使います （サイズ＋先頭と末尾のハッシュ値）。更新日時は使いません。 コピーや再配置によって日時だけが変わったファイルを、不要に読み直さないためです。

状態処理
指紋が前回と同じ読み込みも計算も飛ばす
指紋が違うそのファイルだけ読み直して索引を更新
ファイルが消えた索引から該当分を削除
読み取り方を変えたら「抽出バージョン」を上げること ファイルの内容が同じであれば、アプリ側の読み取り方（Wordを見出し単位で分割する等）を 変更しても指紋は変わらないため、再処理されません。 形式ごとに _OFFICE_EXTRACTION_VERSION などの版数を持たせてあるので、 読み取り方を変えたらこの数字を1つ上げてください。該当形式のファイルだけが読み直されます。 この対応を行わないと、コードを変更しても検索結果に反映されません。

4.2 索引IDの規則

各断片には「資料の種類＋ファイル名＋位置」からIDを作ります。 ファイル名は必ず NFC正規化してから使います。 macOSはファイル名の濁点を分解して保存する（NFD）ため、 正規化しないと同じファイルが別物として扱われ、開発機と配布先で索引の整合が取れなくなります。

4.3 外部データの更新方式

方式意味件数
window直近N期間を毎回取り直す（改定が入る統計）6
snapshot最新時点で丸ごと置き換える4
merge既存に新しい分を継ぎ足す2

定義は refresh_policy.POLICIES にあります。

5検索索引（RAG）の内部

5.1 検索の流れ

  1. 質問の解釈：会話の言葉（「その2点目は？」）のままでは検索に当たらないため、 LLMで自立した検索語に直す（ai_prompts.interpret_messages）
  2. 2種類の検索を並行実行：SQLite FTS5 による全文検索（語の一致）と、 埋め込みベクトルによる意味検索（言い換えに強い）
  3. 統合と並べ替え：両者の結果を突き合わせて上位を選ぶ
  4. 回答生成：選んだ断片を根拠としてLLMへ渡す
  5. 原本へのリンク：evidence.py が断片から元ファイルを引き当て、 画面から原本を開けるようにする

5.2 意図的に索引へ入れないもの

  • README.md などの案内文（資料ではないため）
  • JSON・Markdown 全般（台帳・設定ファイルの誤取り込みを防ぐため）
  • パイプラインが持つ管理ファイル（manifest.json など）

5.3 株主総会議事録フォルダだけ読み方が違う

ファイル読み方理由
過去質疑応答一覧.xlsx1行＝1問として読む 「過去に何を聞かれたか」を論点ごとに引けるようにするため
その他のWord・PDF見出し単位に分ける 議事録の該当箇所を根拠として示すため

論点の出現回数や直近に問われた回次は保存していません。 Excelの行を足し引きするたびに数え直すため、集計がずれることがありません （agm/repository.py の _derive()）。

6LLM連携

6.1 2系統の呼び出し口

関数失敗したとき使う場面
chat() / chat_json() 例外を送出する内部処理。呼び出し側で握りつぶさない場合
call_chat() / call_chat_json() 例外を出さず LLMResult を返す 画面。「AIが答えた」のか「AIを呼べなかった」のかを区別して表示するため
result = ai_client.call_chat_json(messages, feature="agm.answer")
if not result.ok:
    # result.status に unconfigured / http_401 / timeout / refusal などが入る
    # 画面は「AI未接続」の但し書きを出す

6.2 一時的な失敗の再試行

429・5xx・ネットワーク断・タイムアウトは指数バックオフ（1秒 → 2秒）で最大3回試します。 回復しなければ従来どおり失敗として扱います。 計画診断・シナリオ分析・質問予測は待ち時間120秒で動くため、 タイムアウト再試行の上限もそこに合わせてあります （60秒のままだと「一番重くて一番落ちやすい処理だけ再試行されない」状態になるため）。

6.3 JSON形式での受け取り

Bedrock経由のClaudeにはJSON専用モードがないため、システム指示で 「JSONオブジェクトを1つだけ、前置きもコードフェンスも付けずに返す」よう求め、 受け取り側でコードフェンス付きでも拾えるようにしています。

6.4 モデルの切り替え

→ タブ1の変更点3に詳述しています。要点だけ再掲します。

  • 切り替えは .env の ANTHROPIC_MODEL 1行
  • モデルごとの作法は ai_client.MODELS が持ち、送信時に自動で合わせる
  • 候補の確認は python3 ai_client.py、実測は --probe

7画面の作り（Gradio）

7.1 画面切替

14画面すべてが1つの Gradio Blocks の中にあり、 表示の切り替えはブラウザ側のJavaScript（showView()）で行います。 サーバーへの再描画要求が発生しないため切り替えが速く、 入力途中の内容も保持されます。

7.2 HTML → Python の橋渡し（プロキシ方式）

自前で組み立てたHTML内のボタンからPythonの処理を呼びたい場合、 画面上は見えない Gradio のボタン（プロキシ）を置き、 HTML側のクリックでそれをJavaScriptから押します。 Gradio のイベント配線を通るため、状態管理が壊れません。

7.3 セッションの分離

利用者ごとの状態は Gradio の gr.State に持たせ、 モジュールのグローバル変数には置きません。 複数人が同時に使ったときに他人の入力が混ざるためです。

8拡張のしかた

8.1 内部データの分類を増やす

data_internal/ にフォルダを作るだけです。コード変更は不要 （→ タブ1の変更点2に手順）。

8.2 外部データソースを増やす

  1. collectors/ に取得処理を追加する
  2. data_source_config.py に定義を追加する
  3. APIキーが要る場合は settings.CREDENTIALS に登録し、 .env.example にも行を足す
  4. refresh_policy.POLICIES に更新方式（window / snapshot / merge）を書く

8.3 プロンプトを変える

ai_prompts.py の該当する関数だけを直します。 呼び出し側は変更しません。画面側のファイルに文面を書かないでください。 tests/test_llm_switching.py がこれを検査します。

8.4 LLMを切り替える／候補を増やす

切り替えは .env のみ。候補を増やす場合は ai_client.MODELS に1行足し、.env.example にも書きます （この2つがずれるとテストが落ちます）。

8.5 画面を増やす

  1. ui.py に画面HTMLを組み立てる関数を足す
  2. app.py に gr.Column(visible=False) で画面を足す
  3. ナビゲーションに項目を足し、showView() の対象に加える

10守るべき設計上の約束

約束破るとどうなるか
APIキーは .env のみ どれが使われているか追えなくなる。差し替え漏れと流出面が増える
指示文は ai_prompts.py のみ 同じ文面が複数箇所に分散し、一方だけが修正された状態になる
取り込みは pipeline.py 経由 検索に反映される条件が経路ごとに変わり、未反映時の原因を特定できなくなる
ダミーの数値を書かない 画面の数値が実測値か仮の値かを判別できなくなり、経営判断の根拠として使えなくなる
読み取り方を変えたら版数を上げる コードを変更しても検索結果に反映されない（→ 4.1）
ファイル名はNFC正規化する macOSとLinuxで同一ファイルが別のものとして扱われる（→ 4.2）
利用者の状態は gr.State へ 複数名が同時に利用した際、他の利用者の入力が混在する
reset_runtime.py は作業データを消します AIとのやり取りの履歴、想定質問の予測結果、生成レポート、ログを削除します （検索用DBと資料は残ります）。実行前に --dry-run で対象を確認してください。
