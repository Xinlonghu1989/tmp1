2全体像

データの流れは2本です。外部データはパイプラインが自動で取りに行き、 内部データは人がフォルダへ置きます。どちらも最後は検索索引と画面に合流します。

設計の中心にある3つの約束

  1. データの置き場は3つだけで、役割で分ける（外部＝自動／内部＝手動／出力）
  2. 取り込み口は pipeline.py だけ。画面からのアップロードも同じ場所・同じ経路を通る
  3. 数値を作らない。取得できていない指標は「取得待ち」「未連携」と表示し、それらしい値で埋めない

3データパイプライン

このアプリでいちばん重要な部分です。ここの構造を崩す変更は入れないでください。

パスの定義は settings.py の1か所です。環境変数 EXTERNAL_DATA_DIR / INTERNAL_DATA_DIR / PUBLIC_DATA_DIR で変更できます。

草案・総括レビュー・テスト資料は data_internal/中期経営計画/ に置かない。計画点検・グループ横断のサンプルは assets/demo/、実運用の草案や比較資料は画面アップロードで扱う。登録済み確定版の候補は registered_plan_choices() がファイル名の確定／承認／final判定で抽出し、計画期間の終端年→更新日時の降順で並べる。

3.2 コマンド

python3 pipeline.py update             # 外部取得 → 内部取込 → 総会QA資料 → 索引を差分更新
python3 pipeline.py update --internal  # 手で置いた資料だけ反映（数秒）
python3 pipeline.py update --external  # 外部データだけ取得（索引は触らない）
python3 pipeline.py update --agm       # 総会QA資料（株主QAデータ/）だけ台帳へ差分反映
python3 pipeline.py update --force     # 期限前でも外部を全件取り直す／総会QA資料を全件再取込
python3 pipeline.py update --actor 山田 # 更新ログに残す実行者名（省略時 cli:<OSユーザー>）
python3 pipeline.py status             # 分類別の件数、台帳の状態（要確認・失敗）、直近の更新ログ
python3 pipeline.py rebuild            # 索引を作り直す（モデル・抽出設定を変えたとき。約30分）

総会QAの正本は 株主QAデータ/株主総会Q&A資料_<期>期/<コア>/ です。取込対象はPDF（文字情報を持つもの）・docx・doc・目次xlsxで、PDFは knowledge_rag._extract_pdf_pages と同じ抽出器から既存のQ&A構造化処理へ渡します。画像だけ・破損PDFは解析対象外として取込結果に残し、PPTXは総会QAでは対象外です（一般資料RAGのPPTX対応とは別経路）。

管理者機能（データ管理）の「最新データを反映」は同じ pipeline.update_internal / update_agm を呼び、結果は同じ更新ログ runtime_data/ops_log.db（ops_log.py）に 「いつ・誰が・どのデータを・どう更新したか」として残ります。実行者は画面ならログインユーザー、 コマンドなら cli:<OSユーザー>、ホームの自動更新は system:auto。

update は取得に失敗した取得元があると終了コード1を返します。cronの失敗検知に そのまま使えます。画面の 更新期限を確認 ボタンも同じ判定 （pipeline_service.run_pipeline()）を通ります。

3.4 外部データの更新方式

ソースごとの更新周期と方式は refresh_policy.py の POLICIES が持ちます。 取得条件の既定値は collectors/config.json、画面で保存した条件は runtime_data/data_source_settings.json にあり、後者が優先されます （collector.effective_target_settings()）。

mode意味該当ソースの例

snapshot最新スナップショットで置換大阪市推計人口、不動産価格指数、建設資材、Wikipedia（4件）
merge主キーで差分を統合株価、短期滞在入国者数（2件）

取得結果は data_external/monitoring_targets/target_run_manifest.json に記録されます。 取得失敗時は直前の成功結果を維持し、画面には「前回値」と表示します。マニフェストに 記録された絶対パスは settings.relocate_runtime_path() が現在のフォルダへ読み替えるため、 開発機とEC2をまたいでも有効CSVを正しく参照できます。

5設定・APIキー・アクセス権限

APIキーの置き場はアプリ直下の .env ただ1つ 親フォルダの資格情報ファイルや env.txt を参照する旧構成は廃止しました。 鍵を複製すると更新漏れと流出面が増えるためです。

参照は settings.credential() 経由に統一しています。os.environ の直読みは 残していません。参照できるキーの一覧・用途・必須かどうかは settings.CREDENTIALS が 唯一の定義で、起動時に未設定のキーがログへ出ます。

# settings.py
CREDENTIALS = {
    "ANTHROPIC_API_KEY": {"required": "yes", "label": "...", "used_by": "AI機能すべて"},
    "FRED_API_KEY":      {"required": "no",  "label": "...", "used_by": "為替（ドル円）"},
    ...
}

# 使う側
api_key = app_settings.require_credential("FRED_API_KEY")   # 無ければ理由つきで落ちる
value   = settings.credential("ANTHROPIC_BASE_URL")         # 任意のキー

新しい提供元を足すときは、まず CREDENTIALS に1行足してから collector 側で使います。 未登録の名前を credential() に渡すとその時点で KeyError になります。

鍵と接続先は必ず同じ出所から取る settings.load_env_file() は os.environ.setdefault なので、 端末に ANTHROPIC_BASE_URL が export されていると .env の値より優先されます。 「.env のBedrockの鍵 ＋ 端末の公開APIのURL」というちぐはぐな組み合わせになると 必ず401になり、しかも起動ログは正常に見えます。 ai_client.base_url() は「鍵が .env 由来なら接続先も .env」という規則で これを防いでいます。回帰テストは tests/test_credentials.py。

起動ログに接続先ホストを出しているので、事故が起きていれば一目で分かります。

[OK] LLM: 接続設定あり（model=anthropic.claude-opus-4-8／接続先=bedrock-mantle.ap-northeast-1.api.aws）
[OK] APIキー: 8件すべて設定済み
[情報] RAG索引: 有報11件 / 内部資料462件 （model=cl-nagoya/ruri-v3-30m）
ひな形の行末コメント .env.example をコピーして使う運用のため、load_env_file() は 「空白のあとの # 以降」を値から落とします。RAG_ANSWER_DOCUMENTS=6 # 経営AI相談 をそのまま写しても壊れません。空白を挟まない # は値の一部として残るので、 パスワードに使えます。

5.1 アカウント単位のアクセス権限（access_control）

認証（誰か）はGradioのBasic認証が担い、資格情報は権限台帳のパスワード （管理画面で設定・PBKDF2ハッシュ保存）と .env の APP_CREDENTIALS の2系統を併用できます （照合は台帳→.envの順、access_control.verify_login()）。 認可（何を見てよいか）は権限台帳 runtime_data/access_control.db が唯一の根拠です （access_control.py）。旧 AGM_PERMISSION_MODE / AGM_USER_ROLES は廃止しました。 キーは認証済みユーザー名の文字列なので、認証をSSO等へ差し替えても台帳側は無変更で済みます。

台帳は1人1行で、3つの層を持ちます（2026-09-05 再設計）。付与は明示のみで、役割による 暗黙の全データ付与はありません。

層項目効くところ
システム管理者is_admin管理者機能（データ管理・権限・ログ）。全データ・全機能を見られる
経営診断の付与user_grants：データ群＝data_internal/ のフォルダ名、機能群＝事業KPI:<事業>検索・根拠に使える資料、センシングボードに出る事業（許可のない事業は施錠カード）
総会QAの役割role（bu_core／secretariat／executive／none）と agm_core（担当BU＝資料フォルダのコア名）総会QAアプリの画面と閲覧範囲。コアBUは担当BUの問答だけ

台帳に無い・無効な利用者は deny-by-default：公開IR資料（有報・統合報告書・公式IR資料・外部事例）だけを閲覧でき、 総会QAアプリの操作はすべて拒否されます。付与できるデータ群は data_internal/ のフォルダ名から動的に導きます （restricted_groups()）。フォルダを増やせば付与候補にも自動で並びます。 内部KPIの数値・指標名はページのHTMLにも埋め込まれません（ui.sensing_html(allowed_names) がサーバー側で除外）。 upsert_user() は None の項目を変更しない部分更新で、経営診断画面と総会QA画面が同じ行を分担して更新します。 コマンド manage_users.py（list / template / export / import / add / set-password / deactivate / delete）は 同じ台帳を読み書きし、実行者 cli:<OSユーザー> として監査ログに残ります。

権限設定の手順（運用） ① .env に APP_ADMIN_USERS=<管理者のユーザー名> を1行設定して起動 （台帳が空でも管理者機能へ入れる入口・締め出し防止）。
② 管理者でログイン → 左レール下部「管理者機能」→ 経営診断タブ「ユーザー権限管理」でユーザー名（＝ログインID）・ 表示名・パスワード・有効・システム管理者・データ群・機能群を設定して保存。保存した瞬間から反映（再起動不要）。
③ 総会QAを使う利用者は、総会QAアプリ タブ「ユーザー権限管理」で役割（コアBU／事務局／役員）と担当BUを付与。 台帳は1行に両方が並ぶ（CSVダウンロード可）。
④ 大量登録・一括変更は manage_users.py template > users.csv → 編集 → manage_users.py import users.csv （無い列は変更しない。パスワードは取り込み時だけ受け付ける）。
⑤ 変更はすべて audit_log に記録され、同画面の「権限の変更履歴」で確認できます （パスワードは設定した事実だけを記録し、値は残しません）。
⑥ 退職・異動は「無効化」＝ログイン不可にする（行は残る＝履歴の突合が壊れない）。 行ごと消してよい場合だけ「削除」を使う（監査ログに削除の記録は残る）。

強制ポイントは7系統に集約しています。新しい取得経路を作るときは必ずどれかを通してください。

経路実装
RAG検索knowledge_rag.retrieve(..., allowed_groups=)。SQLのWHEREで 順位付け前に絞る（_ACCESS_GROUP_SQL）。Noneはシステム内部呼び出し専用
AI相談・計画点検data.assistant_reply(..., username=) がハンドラの gr.Request.username から許可集合を解決して伝搬
株主総会の操作agm/ledger.role_for_user() が台帳ロールを工程権限へ写像。 未登録はviewerで全操作拒否
管理者機能ハブと各画面の描画・操作は access_control.is_admin() のみ。画面からの資料登録・削除は廃止（フォルダ直置きが正本）
AI回答履歴response_store.list_records(username=)。本人のみ、管理者だけ全件
計画点検の補助参照議事録・実績資料をプロンプトへ注入する _past_meeting_reference / _actual_state_reference と、監視カタログの _premise_reference、UC6の「登録済みの計画」参照。すべて利用者の 許可データ群・事業KPIで絞る
センシングボードui.sensing_html(allowed_names)＋監視設定4ハンドラ。 事業KPI群で事業体単位に強制
プロンプトへの注入は「検索」と同じ強制ポイントである RAG根拠（assistant_reply(username=)）だけを絞っても、ワークフローが extra_context で議事録や実績資料の本文を直接注入すれば、レポートに そのまま引用されて漏れる（実測: 権限のない利用者の計画点検レポートに 経営会議議事録が載っていた）。内部データをAIへ渡す経路を新設するときは、 必ず allowed_groups（と必要なら事業KPI）を受け取り強制すること。 回帰テストは tests/test_core.py::PlanWorkflowAccessTest。
ローカル開発の全権は ALLOW_NO_AUTH=true のときだけ 認証なし起動時の表示名「ローカルユーザー」を管理者として扱うのは ALLOW_NO_AUTH=true の場合のみです（access_control._dev_admin()）。 以前あった「request欠落→事務局へ自動昇格」の経路は廃止しました。 テストは各ファイル冒頭で os.environ["ALLOW_NO_AUTH"]="true" を設定しています。 回帰テストは tests/test_access_control.py。

6検索索引（RAG）の内部

6.1 索引の対象

索引に入る資料の列挙は knowledge_rag.document_sources() の1か所だけです。 ここがフォルダを読むので、分類はコードに書かれていません。

source_type対象読み方
internaldata_internal/<分類>/ の資料と、自動取得したHHHD公式IR資料形式ごとに本文抽出
minutesdata_internal/株主総会議事録/ の議事録（Word・PDF）見出し単位に分割
qa_historydata_internal/株主総会議事録/過去質疑応答一覧.xlsx1行＝1問
reportEDINETの有価証券報告書PDFページ単位（取得設定で対象年が変わるため別関数）
case外部事例（Wikipedia由来）1事例1断片

6.1.1 対応形式と分割の単位

knowledge_rag.DOCUMENT_EXTENSIONS が唯一の定義です。画面のアップロード欄 （app.ALLOWED_UPLOAD_SUFFIXES）もここから引いており、両者は必ず一致します （ずれると「登録できたのに検索に出ない」という分かりにくい状態になります。 回帰テスト: test_data_pipeline.test_upload_filter_matches_indexable_formats）。

形式分割の単位実装
.pdfページ_extract_pdf_pages()（pypdf → pdfminer の順に試す）
.docx見出し_docx_sections()。w:pStyle の Heading1〜4／見出し1〜4 を検出
.pptxスライド_pptx_sections()。ppt/slides/slideN.xml の a:t を拾う
.xlsx / .xls / .csvシート・行worksheet_rows() → _tabular_rows()
.txt全体そのまま読む

Word・PowerPointはどちらも標準ライブラリの zipfile ＋ ElementTree で 読んでいます。読み取り専用に python-docx / python-pptx を足していません （依存を増やさないため。書き出しには python-docx を使います）。

PowerPointは、内部資料への登録前と対話添付時の両方で、ZIP展開後の総サイズと スライドXML本文の合計サイズを検証します。ppt/presentation.xml を持たない破損・偽装ファイルは 受け付けず、抽出対象はスライド本文だけです（図に埋め込まれた文字、ノート、アニメーションは対象外）。

JSON・Markdownは資料として扱いません 業務部門がやり取りする形式ではないうえ、台帳や設定ファイルを資料と誤認する原因になります。 実際、JSONを無条件に読んでいた頃は同期台帳 manifest.json の生テキスト105断片が 検索対象に紛れ込んでいました。README.md（フォルダの案内文）も _NOT_A_DOCUMENT で除外しています。
抽出方式を変えたら、その形式の版を上げる ファイルの中身が同じだと署名が変わらないため、抽出の作りを変えても再抽出されません。 表なら _TABLE_EXTRACTION_VERSION、Word・PowerPointなら _OFFICE_EXTRACTION_VERSION を上げます（_source_signature() が その形式のファイルにだけ版を混ぜるので、PDF 467件は巻き添えになりません）。

6.2 断片IDの規則

internal-<sha1(NFC正規化したファイル名)[:12]>-<節>-c<連番>
report-<PDFのstem>-p<ページ>-c<連番>
minutes-<sha1(NFC名)[:12]>-s<節番号>-c<連番>
qa_history-<sha1(NFC名)[:12]>-<レコードID>
ファイル名は必ずNFCへ正規化する macOSは濁点を分解した形（NFD）でファイル名を返します。正規化せずにSHA1を取ると、 同じ資料でも開発機とEC2で別IDになり、配布した索引がそのまま使えません。 実際に公式IR資料468件中318件がこれで壊れていました。正規化は knowledge_rag._document_key() の1か所に集約しています。
ID規則を変えたら _ID_SCHEME_VERSION を上げる 上げないと、内容ベースの指紋が一致して早期リターンし、 旧IDの行が残ったまま新IDの行が入らない「半分だけの索引」になります。 この版は _fingerprint() と _build_params() の両方に入っており、 上げれば自動で作り直されます。

6.3 埋め込みモデル

knowledge_rag.EMBEDDING_MODEL = "cl-nagoya/ruri-v3-30m" に固定です（2026-09-06 に hotchpotch/static-embedding-japanese から差し替え）。環境変数では変えられません。 静的モデルは索引が速い一方、語順・文脈を見ないため言い換え・口語の質問で語彙の壁を越えられず、精度評価（168問）で A Recall@8 66.7%→71.7%、総会QAの別回次一致 55.3%→78.9% の差が出ました。ruri-v3 は入力上限8,192トークンで ページ相当のチャンク（最大2,700字）が切り捨てられません。質問・文書に接頭辞（「検索クエリ: 」「検索文書: 」）を 付けて埋め込みます。接頭辞はモデル系列名の先頭一致で引く表 _EMBEDDING_PREFIXES だけに置き、他所にモデル別の分岐は作りません。

差し替えるときはこの定数を書き換えて pipeline.py rebuild を実行します。 索引はモデル名を記録しており、一致しないあいだは意味検索を使わず語彙検索だけで応答します（別モデルのベクトルを混ぜない）。 検索の内側では全件の作り直しをしません（ensure_index(allow_full=False)。以前はモデル変更後の最初の検索が 全件を再計算し、利用者の検索が数十分止まる構造でした）。差し替え後は scripts/eval_search.py calibrate で 類似度の分布を測り、knowledge_rag._SCORE_SCALES（関連度の強・中・弱の境界、「根拠なし」判定の下限、 意味だけで候補に残す下限）にモデル系列の行を足します。尺度に依存する閾値はこの表だけにあります。

資料台帳（rag_files、rag_registry.py） ― 索引に入れた資料1件ごとに種別・対象期・事業・ 抽出品質・状態を持ちます。読み取りは規則（題名・ファイル名の定型表現）→ LLM（規則で決まらない資料だけ、本文冒頭を1回）→ 手書きの上書き（runtime_data/rag/registry_overrides.json）。台帳の期は断片のメタデータ （p_fy/p_y/p_m）へ写り、期一致・版選び（「直近の」）の入力になります。絞り込みには使いません。 状態は 正常／要確認（本文200字未満）／失敗（開けない）／除外（外国語版）で、管理者機能のデータ管理と pipeline.py status に理由つきで出ます。中身が同じ資料の読取結果は全件の作り直しでも使い回します。

根拠なし判定 ― 相対カットオフは「最良との比」で切るため、無関係な質問でも候補が並びます。最良ヒットの意味類似度が 尺度表の下限（ruri-v3: 0.85）を割るか、意図解釈が「社内資料と無関係な依頼」（uses_internal_documents=false）と 判定したときは、根拠欄に注意書きを出し、回答プロンプトへも「関連の薄い資料を引用しない」指示を渡します （evidence_is_weak）。検索結果そのものは消しません。

索引の書き換え中も検索は直前の索引を読みます（SQLite WAL。コミット後に本体へ畳む）。書き換えが途中で止まっても旧索引は無事です。

6.4 検索の流れ

  1. 候補の絞り込み ― SQLite FTS5で最大600件（RAG_CANDIDATE_LIMIT）。 アクセス権限の許可データ群（allowed_groups）はこの段階のWHEREで絞る。 期を名指しされたら該当メタデータの断片を、期のない話題型（ホテル×稼働率 等）は 該当月次シリーズの断片を、語の一致に頼らず候補へ直接注入する （_period_candidate_ids / _topic_series_markers。 表中心の月次号は語彙・意味の両検索から漏れるため）
  2. 再評価 ― 候補だけを埋め込みで採点し、意味0.9＋語彙0.1で融合。 資料が増えても全断片を毎回読まない
  3. 期・名指しの優先 ― クエリの年月・◯年3月期・四半期・第N期・第N回を読み取り、 索引メタデータ（p_y/p_m/p_fy/p_q/p_ki/p_no）と構造比較で一致する資料へ加点。 資料名の名指し（「統合報告書2023」＝数字を含む題名区分がクエリに現れる）も号の特定として扱う。 号まで特定した資料はほぼ最良の帯（PERIOD_MATCH_FLOOR_RATIO=0.96）へ、 系列だけの一致は一段下の帯（SERIES_MENTION_FLOOR_RATIO=0.70）へ引き上げる。 年度単独の一致は、資料種別の指し示しと併さったときだけ号の特定とみなす （一律に確定扱いすると同一年度の短信・説明会・株主通信が一斉に持ち上がり、 有報層のRecall@5が60%→5%へ崩落した実測がある）
  4. シリーズ多様化 ― 年度・月違いの同型資料（決算説明会等）は上位2件まで （RAG_SERIES_CAP）。号まで名指しされた資料（_period_exact）は対象外。 系列一致だけの資料は対象のまま（でないと話題一致で月次号12冊が上位を占有し直す）
  5. 足切りと確信度 ― 最良の55%未満を除外（RAG_RELATIVE_RATIO）。 最良でも弱ければ根拠欄に「⚠ 強く関連する社内資料は見つかりませんでした」。 関連度は強・中・弱の3段表示（relevance_label。無関係クエリの実測分布で較正）
  6. 資料単位へ集約 ― 同じ資料の断片を畳み、前後ページを付ける（RAG_NEIGHBOR_PAGES）。 evidence.build() が資料ラベルと該当箇所を解決してプロンプトへ
期メタデータは索引時に自動付与 _insert_documents() が全ソース共通で題名・ファイル名・本文冒頭から期を構造化します （有報はハッシュ名で期が題名に無いため、表紙の「第188期（至 2026年3月31日）」を本文から読む）。 照合を文字列一致に頼ると「2021年度(2022年3月期)」の年数字が誤爆します。
検索語の選択則（answer_markdown） 単発の質問は利用者の原文だけで検索します（自然文は意味照合に最も強い）。 会話の続きは指示語（「その2点目」）が残るため、意図解釈で書き換えた検索語を主、 原文を副とした重み付きランク融合（retrieve_fused、RRF）を使います。 書き換え語だけで検索してはいけません——キーワード列は系統的に高いコサイン値を出し、 内部資料80%→60%・株主総会の論点一致42%→16%へ悪化します（実測）。
精度の測り方 python3 scripts/eval_search.py run で、正解付き168問（scripts/eval_gold.jsonに固定）の Recall@5/@8・MRR・足切り誤殺率を数分で再計測できます。検索パイプラインを触ったら 必ず前後で回して差分を確認してください。評価レポートは別紙。

原本へ戻れることが信用の前提です。索引はファイル名しか持たず、置き場所は evidence._locate() が data_internal/ と data_external/ を走査して解決します （結果はキャッシュ、外れたときだけ作り直し）。Evidence.verifiable が False の根拠は 断定の材料にしません。data_internal/ はGradioの静的配信対象に含めません。利用者への表示は allowed_groups を適用したRAGの資料名・ページ・抜粋だけであり、原本を画面から提供する場合は、 別途リクエストごとに認可する配信経路を実装してください。

6.5 意図的に索引へ入れないもの

英語版のIR資料（Integrated Report、Notice of Convocation など）は日本語版と重複するため、 is_foreign_edition() が除外します。判定は「本文の先頭3,000字の日本語比率が2%未満」かつ 「資料名にかなが無い」の両方で、片方だけでは誤ります。本文が200字未満の資料は外国語判定せず、 資料台帳の品質ゲート（「要確認」）へ回します（かなの無い名前の画像PDFが黙って除外され、再試行もされなかったため）。 除外・要確認・失敗は資料台帳に理由つきで残り、pipeline.py status（!＝未索引、?＝要確認・失敗）と 管理者機能のデータ管理に出ます。

7LLM連携

接続は ai_client.py に集約しています。呼び出し口は2系統です。

入口失敗時使いどころ
chat() / chat_json()例外を送出従来の呼び出し
call_chat() / call_chat_json()LLMResult を返す推奨。「AIが答えた」のか「AIを呼べなかった」のかを区別できる

LLMResult.generated_by が llm / unconfigured / error のどれかを示します。 画面はこの値を見て「AI未接続」などの但し書きを出します。API未設定・通信失敗・JSON不正のときも 画面操作は中断しません。RAG検索結果または規則ベースの後備表示に落ちます。

再試行は429・5xx・接続断・タイムアウトのみ、バックオフは (1.0, 2.0) 秒。 プロンプトは ai_prompts.py に集約し、すべて messages 形式を返します。 共通ルール（根拠のない数値を作らない、「実データ／取得待ち／未連携／資料記載／AIの推論」を 区別する）は _common_system() にあります。

対話モードは必ず ASSISTANT_PROMPT_BUILDERS へ登録する assistant_messages() は未登録のモード名を黙って自由質問へフォールバックさせます。 計画点検の6モードがこれで雑談用プロンプト（簡潔さ優先・出力2,500トークン）に落ち、 報告書が上限に張り付いて圧縮される事故が実際に起きました。診断系は MANAGEMENT_REVIEW_MODES（報告書ビルダー・出力8,000・タイムアウト120秒）、 文案修正は data._effective_assistant_mode() が草案作成支援へ振り替えます。 新モードを足したら tests/test_ai_prompts.py に登録検査を追加してください。

7.1 モデルの切り替え

使用するモデルは .env の ANTHROPIC_MODEL 1行で切り替わります。 プロンプト（ai_prompts.py）も呼び出し方（chat / chat_json）も 変更は要りません。

python3 ai_client.py          # 候補の一覧と使用中のモデル
python3 ai_client.py --probe  # 接続先が本当に応答するかを実測

モデルによって送信の作法が違うため、その差は ai_client.MODELS という表に 持たせ、送信時に自動で合わせています。切り替えのたびに呼び出し側を直す必要はありません。

項目意味放置するとどうなるか
available この接続先が実際に提供しているか 未提供のIDを書くと 404 does not exist
temperature 温度指定を受け付けるか（Opus 4.7以降は廃止、Haiku 4.5は可） 受け付けないモデルへ送ると400で全AI機能が停止
thinks_by_default 思考が既定でONか（Opus 5 / Sonnet 5）。思考分も出力上限に数えられる 出力枠を広げないと回答が途中で切れる
max_output 1回の応答の上限 超えると400

また、新しい世代は安全性の判断で回答を控えることがあります。このとき通信は HTTP 200 で本文が空になるため、ai_client.RefusalError として明示的に失敗扱いにし、 LLMResult.status に refusal が入るようにしています （空文字を「AIが答えた」と誤認させないため）。

候補を増やすときは2か所を同時に直す ai_client.MODELS に行を足し、.env.example にも書きます。 tests/test_llm_switching.py がこの2つの一致を検査するので、 片方だけ直すとテストが落ちます。
同じテストが「AIへのメッセージ組み立てが ai_prompts.py の外に無いこと」も 検査しています。画面側に文面を書かないでください。

8画面の作り（Gradio）

全27ビューが1つの gr.Blocks に同居し、表示切替はクライアントJSで行います。 Python側は画面の切り替わりを知りません。

8.1 画面切替とナビゲーション

showView('sensing') のようなJS関数がCSSクラスを付け替えるだけです。 各ビューは elem_id="view-<名前>" を持ちます。現在地はURLハッシュ （/#agmhome 等）と同期し、リロードしても同じ画面へ戻ります。

左レールは「持ち場の切替」と、下部の「フィードバック」（全員）・「管理者機能」（システム管理者）だけを持ちます （経営診断⇄総会QAアプリの切替ボタン＋ログアウト。旧「管理者設定」の折り畳みは廃止）。管理者機能はハブ （経営診断／総会QAアプリの2タブ）から各画面（データ管理・ユーザー権限管理・AI入出力ログ・エラー管理）へ開き、 画面を足すときは admin_ui のカード、パンくず、showView の一覧、ADMIN_REFRESH の4か所を揃えます。機能への入口は各ホームのカードが担い、 経営診断は workflow_catalog.HOME_MENU、総会QAアプリは6工程の番号付きカード （workflow_catalog.AGM_MENU → view-agmhome）です。旧・3階層の左メニューは ホームのカードと完全に重複していたため廃止しました。戻る動線は「一つ上の階層」へ返す 構造ナビ（JSの VIEW_PARENT）です。

8.2 HTML → Python の橋渡し（プロキシ方式）

gr.HTML の中に置いたボタンからPythonを呼びたい場合、隠しボタンを経由します。

# app.py：隠しボタンを置く
proxy_rules_open = gr.Button("", elem_classes="hh-hidden", elem_id="proxy-rules-open")

# クライアントJS：引数を State へ書いてから隠しボタンを押す
window.hhOpenRules = function(key){
  ...
  setTimeout(function(){ hhClick('proxy-rules-open'); }, 60);
}
イベントに .then(None, None, None, js=RUN_JS) を忘れない gr.HTML 内のスクリプトは再描画のたびに hhRun() を通さないと動きません。 付け忘れるとエラーも出ずに静かに動かなくなります。
gr.HTML を visible=False にしない Gradio 6では、イベント出力で gr.HTML を visible=False にすると スピナーが永久に表示されます。表示切替は fn=None ＋ js のクライアント専用イベントと CSSクラスで行うのがこのアプリの流儀です。

8.3 並行制御

重い処理は concurrency_id で直列化します。

ID対象
rag-write資料の登録・削除（索引の書き込み）
diagnosis-ai計画診断のAI生成
agm-predict / agm-review株主総会の質問予測・点検
source-viewデータソースの単体更新

プロセスをまたぐ排他は settings.exclusive_runtime_lock(name) が runtime_data/.<name>.lock の原子的生成で行います（失効7200秒）。 cronの pipeline.py update と画面からの更新が競合してもここで防げます。

8.4 セッションの分離

会話履歴は gr.State のみで保持し、ディスクへ永続化しません。リロードで消えます。 一方、監視設定・取得条件・フィードバックは組織で1つの設定なので全利用者で共有されます （誰かが閾値を変えれば全員の画面に反映されます）。

9拡張のしかた

9.1 内部データの分類を増やす

コード変更は不要です data_internal/ にフォルダを作るだけ。settings.internal_categories() が 直下のフォルダ名を読むので、pipeline.py status にも画面のアップロード先プルダウンにも 自動で並びます。 
mkdir data_internal/取締役会資料
# 資料をこのフォルダへ入れる
python3 pipeline.py update --internal
python3 pipeline.py status

settings.INTERNAL_CATEGORY_SEED は初回に空フォルダを作るための一覧にすぎず、 分類の定義ではありません。

アクセス権限との関係（2026-08の権限台帳導入後） フォルダ名＝分類名＝アクセス制御のデータ群名です（例外: 「IR公表資料」フォルダは 公開IR扱いで全員閲覧可）。付与候補は access_control.restricted_groups() が フォルダ一覧から動的に導くため、フォルダを作れば管理画面の付与候補にも自動で並びます。 ただし deny by default のため、新フォルダの資料が見えるのは「内部全分類」ロール （経営層・事務局・管理者）と、管理画面でその群を個別付与されたユーザーだけです。 担当・コアに見せる場合は付与を忘れずに。索引の期メタデータ（§6.4）は 取り込み時に自動付与されるため、追加作業は不要です。

9.2 外部データソースを増やす

  1. settings.CREDENTIALS にAPIキーを登録する（キーが要る場合）
  2. collectors/collector.py に target_<source>(settings) を書く。CSVを TARGET_DIR/<source>/ へ保存し、結果の辞書（csv_path, rows 等）を返す
  3. 同ファイルの actions 辞書と、その直前のソース名タプルに <source> を追加する
  4. refresh_policy.POLICIES に更新周期（hours）と方式（mode）を足す
  5. data_source_config.SOURCE_SPECS に表示名・提供元・設定フィールドを足す
  6. 画面に出す指標として使うなら pipeline_service._extract_metrics() に変換を書き、 data.CATALOG に指標を登録する
  7. python3 pipeline.py update --external で取得を確認する
指標名の対応表が5か所に分かれています data.METRIC_ALIASES / pipeline_service の bindings / data_source_config.SOURCE_SPECS / series.SOURCES / knowledge_rag._METRIC_CONCEPTS。表記ゆれが既に存在します（「株価」「HHHD株価（9042.T）」など）。 指標を足すときは5か所すべてを確認してください。

9.3 プロンプトを変える

ai_prompts.py の該当ビルダーだけを触ります。構造化出力を返す機能は、 同じ関数内のJSONスキーマ文字列も併せて更新してください。共通ルールを変える場合は _common_system() です。

9.4 画面を増やす

  1. app.py に gr.Column(elem_classes="hh-view", elem_id="view-<名前>") を足す
  2. 入口をホームのカード（workflow_catalog.py）に置き、JSの画面リストと VIEW_PARENT（戻り先）へ追加する。管理者機能に入れる場合は admin_ui の ハブのカード・パンくず（crumb_html）・showView の一覧・ADMIN_REFRESH の4か所を揃える
  3. 描画は ui.py に純関数として書く（Gradioをimportしない）
  4. イベントには .then(None, None, None, js=RUN_JS) を付ける
  5. 利用者マニュアル（doc/利用者マニュアル.html）へ画面名を追記する。 tests/test_management_ux.py がマニュアルと実装の整合を検査します

11守るべき約束と落とし穴

1. データの取り込み口は pipeline.py だけ 別経路を足さない。画面のアップロードも data_internal/<分類>/ へ保存し、 同じ索引経路を通します。経路が2本に割れると、同じ資料が別名で二重に索引されます （実際に起きました）。
2. APIキーの置き場は .env だけ settings.CREDENTIALS に登録してから使う。os.environ を直読みしない。
3. 指標の数値を作らない 未取得は「取得待ち」、未接続は「未連携」。data._ext() / _internal() は 指標名しか受け取らないので、捏造値を書く場所がありません。この形を崩さないでください。
4. 索引IDの規則を変えたら _ID_SCHEME_VERSION を上げる 上げないと「半分だけの索引」になります（6.2）。
5. LLMの鍵と接続先は必ず同じ出所から取る 片方だけ環境変数から拾うと401。起動ログは正常に見えるため気づけません（5章）。

そのほかの癖

  • gr.State の source_editor は画面に出ませんが、出力の個数を揃えるために必要です。外すと配線が壊れます。
  • データソースを切り替えるときは clear_source_plot（value=None）を前段に挟みます。 描画側（Vega）が前のスケールを保持するためです。
  • 時刻は settings.now_local() を使います。datetime.now() はサーバのTZに従うため、 開発機（JST）とEC2（UTC）で記録が混在し、文字列ソートで新しい記録が沈みます。
  • ログに秘密情報を出さないよう、applog.py がキー名（api_key, token 等）で伏字化します。
